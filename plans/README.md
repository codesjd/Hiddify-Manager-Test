## Recommended sequencing

1. **001 first** — it's the safety net (`pytest`) that 005, 010, 011, 012, 014,
   020 build on, and fixes the broken dev-deps install that blocks all testing.
2. **The config-only 512MB wins next** (002, 003, 004) — S effort, LOW risk,
   independent, immediate RAM relief. **006** (config self-test) alongside them —
   it would have prevented the `xPaddingBytes` production outage.
3. **Then the bigger 512MB / reliability items**: 005 (drop Celery, after 001),
   007/008/009 (install reliability).
4. **Correctness sweep**: 010, 012, 013, 014, 015, then 011 (multi-node — needs a
   parent/child staging box to verify) and 016.
5. **Direction spikes last / as capacity allows**: 017 (SQLite — the big
   structural 512MB win; decide vs 002 first), then 018/020, then 019/021.

## Dependency & decision notes

- **002 vs 017 are mutually exclusive for a given install.** 002 = "keep MariaDB,
  make it fit"; 017 = "drop MariaDB for SQLite". Decide the DB direction first. If
  017 ships, mark 002 REJECTED (moot) for SQLite installs. 002 is the safe
  now-win; 017 is the larger structural win (biggest single RAM reclaim) but a
  real feature with concurrency/reconciler risk — hence spike-first.
- **001 before 005/010/011/012/014/020** — they add or rely on the pytest harness.
- **019 after 017/002/003/005** — the big RAM levers are DB/Redis/Celery; the lite
  profile only compounds them and must be measured (Step 1) before implementing.
- **020 pairs with 017** — CI already runs the panel on SQLite, so golden render
  tests slot into that substrate.
- **004 and 006 both touch jinja.py/run.sh** but different lines — either order;
  avoid editing the same hunk twice.

## Considered and rejected (by-design — not findings)

- Disabling a core (xray or singbox) to save RAM — **forbidden** (`PROJECT_SPEC.md`
  §2.1; both must run or sing-box-only protocols die). Violates "no feature loss".
- The schema reconciler's `sys.exit(1)` on non-additive diffs — intentional, no
  bypass by design (§2.4).
- `jinja.py` import-time `json.load(current.json)` silent-no-op — known/recorded
  risk (§6); the write-side is hardened by plan 006, the import-side is a separate
  known item, not re-reported.
- `all_public_ports()` existing in two places — intentional; only the *drift* is a
  finding (plan 014).
- `mysqlclient` + `psycopg` coexistence — legit (MySQL vs Postgres backends); only
  `pymysql` is redundant (plan 016).
- "No live-traffic integration tests" — intentional (sandbox can't run real
  traffic; §7). Only the absence of *offline* unit tests is a finding (plan 001).
